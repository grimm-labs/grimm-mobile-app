# AGENTS.md — Grimm App (grimm-mobile-app)

Guide for coding agents working in this repository. Read it before changing code; keep it up to date when you change something it describes.

## What this is

Grimm App is a self-custodial Bitcoin wallet for Android and iOS (package `com.grimm.labs.app`, public repo `grimm-labs/grimm-mobile-app`). It has two wallets derived from the **same 12-word seed**:

- **Lightning** through the Breez SDK Spark (`@breeztech/breez-sdk-spark-react-native`), with Lightning addresses on `pay.usegrimm.app`.
- **On-chain** through BDK (`bdk-rn` 1.0.0, BIP84 descriptors, Esplora backends).

Other features: BTC price in the user's fiat currency (Yadio), push notifications (own notification service + Expo/FCM), transaction notes (SQLite), EN/FR, light/dark theme.

The project started from the [obytes React Native template](https://starter.obytes.com); many workflows, scripts and comments still reference it.

## Stack

- Expo SDK 53, React Native 0.79 (new architecture on), React 19, TypeScript strict, Hermes
- expo-router 5 (file-based routing in `src/app`, `typedRoutes` on)
- NativeWind 4 + Tailwind 3 (`className`), tailwind-variants for component variants
- State: React Context providers (zustand is a dependency but not used for stores)
- Data fetching: axios + @tanstack/react-query + react-query-kit
- i18next / react-i18next, expo-localization
- Storage: AsyncStorage, expo-secure-store (seed), expo-sqlite (notes)
- Tests: Jest (jest-expo) + React Native Testing Library; E2E: Maestro
- Package manager: **pnpm only** (`pnpm@9.12.3`, `node-linker=hoisted`). CI uses Node 22 (`.tool-versions` still says 20.11.1).

## Commands

```sh
pnpm install                 # never npm/yarn (preinstall runs only-allow pnpm)
pnpm start                   # Metro (APP_ENV=development)
pnpm android | pnpm ios      # build + run a dev build (expo run:*), development env
pnpm android:staging         # same with APP_ENV=staging (also :production)
pnpm prebuild:<env>          # regenerate android/ and ios/ for development|staging|production

pnpm lint                    # eslint (prettier is enforced through eslint)
pnpm type-check              # tsc --noemit on the whole project
pnpm lint:translations       # eslint --fix on src/translations/*.json (sorts keys)
pnpm test                    # jest; single file: pnpm test path/to/file.test.tsx
pnpm test:ci                 # jest --coverage (what CI runs)
pnpm check-all               # lint + type-check + translations + tests

pnpm e2e-test                # Maestro flows against com.grimm.labs.app.development
```

Before handing work back, run at least `pnpm lint`, `pnpm type-check` and the tests touching your change.

## Architecture

### Navigation

- `src/app/_layout.tsx` (root) wraps everything in providers, in this order (outermost first). The order matters because of hook dependencies: `AppContextProvider` → `NotificationProvider` → `WalletErrorBoundary` → `BreezProvider` → `GestureHandlerRootView` → `KeyboardProvider` → `ThemeProvider` → `APIProvider` (react-query) → `BitcoinPriceProvider` → `WalletErrorBoundary` → `BdkProvider` → `BottomSheetModalProvider`. `PrivacyOverlay` sits inside `GestureHandlerRootView`.
- The root `<Stack>` declares `(app)` and `onboarding`. Every other folder (`auth/`, `send/`, `send-onchain/`, `receive/`, `settings/`, `wallets/`, `transaction-details/`…) is an implicit screen of that root stack. `receive-btc/_layout.tsx` and `scan-qr/_layout.tsx` are full screens written as layouts.
- `src/app/(app)/_layout.tsx` is the gate and the wallet bootstrapper. It renders nothing until the data and the language are loaded. If there is no seed (`hasSeedPhrase`), it redirects to `/onboarding`. Otherwise it renders the tabs (`index`, `transactions`, `settings`), starts Breez and BDK, and hides the splash screen.
  - Screens outside `(app)` are not gated. They rely on `(app)` having mounted first.
  - The `onboarding` AsyncStorage flag is saved but never used for routing.
- Onboarding flow: `onboarding.tsx` → "Get started". This asks for notification permission, then goes to `auth/create-or-import-seed.tsx`. From there the user can import a seed via `auth/import-seed-phrase.tsx`. When a seed is created, the app runs `router.dismissAll()` then `router.replace('/')`.
- `+native-intent.tsx` turns `lightning:<invoice>` links into `/send/transaction-details?rawInvoice=…`. Schemes: `GrimmApp`, `lightning`.
- There is no PIN or biometric lock. Privacy features:
  - `PrivacyOverlay` shows the splash image when the app goes to the background.
  - `ScreenCaptureGuard` blocks screenshots when that setting is on.
  - `hideBalance` hides the balance.

### State and storage

| Where | What |
| --- | --- |
| `lib/context/app-context-provider.tsx` (`AppContext`, `useAppContext`) | `hasSeedPhrase`, `isDataLoaded`, `hideBalance`, `preventScreenCapture`, `selectedCountry` (default Cameroon/XAF), `bitcoinUnit`, `isSeedPhraseBackup`, `resetAppData()` |
| `lib/context/breez-context.tsx` (`useBreez`) | Breez SDK lifecycle, balances, payments, LN address, unclaimed deposits, `network` (`AppNetwork.MAINNET/TESTNET`), polls every 10 s |
| `lib/context/bdk-context.tsx` (`useBdk`) | BDK wallet lifecycle, Esplora server selection/fallback, sync every 60 s, send/fee estimation, cached snapshot |
| `lib/context/bitcoin-prices-context.tsx` (`useBitcoin`) | Yadio prices, polled every 20 s while the app is active |
| `lib/context/notification-context.tsx` (`useNotifications`) | Permission status, device registration with the notification service |

- **Seed phrase**: expo-secure-store key `seedPhrase`, accessed with `useSecureStorage('seedPhrase')`. Several providers read it independently. Never log it and never store it anywhere else.
- AsyncStorage keys include `hideBalance`, `preventScreenCapture`, `selectedCountry`, `bitcoinUnit`, `isSeedPhraseBackup`, `appNetwork`, `lnAddress`, `SELECTED_THEME`, `local` (language), `selectedEsploraServer_<network>` and `bdkWalletSnapshot_<network>`. Use the JSON helpers in `lib/storage.tsx`.
- SQLite `grimm-local.db` (`lib/sqlite`): table `transaction_notes`, with keys `ln:<id>` / `onchain:<txid>`.
- `resetAppData()` (logout) does not clear everything. The country, theme, language, network, Esplora server, BDK `.db` file and Breez `spark-data` all survive it.

### Wallets and networks

- The UI exposes `mainnet` and `testnet`. **Testnet means Breez `Regtest` and BDK `Network.Testnet`.** The Esplora testnet URLs in `lib/constant.ts` mix testnet4 and testnet3 servers. Check this before touching network code.
- Esplora servers are listed in `DEFAULT_ESPLORA_SERVERS` (`lib/constant.ts`), with the default server first. On HTTP 429 the app falls back to the other servers.
- BDK wallet DB: `${documentDirectory}bdk-wallet-<network enum>.db`. `estimateTransactionFee` builds and signs a real transaction to measure its size.
- `bdk-rn` is imported at module load by `BdkProvider`. Its native library exists **only for `arm64-v8a`** on Android (see "Gotchas").

### API and environment variables

- There are two sides to env handling:
  - The root `env.js` (Node, build time) loads `.env.<APP_ENV>` with dotenv. `APP_ENV` defaults to `development`, and all scripts set `EXPO_NO_DOTENV=1`. It validates with zod and **throws if a variable is missing** (`NOTIFICATION_API_URL` must be a URL). `app.config.ts` puts the client variables in `extra`.
  - In app code, import `{ Env } from '@env'` (`src/lib/env.js` reads `Constants.expoConfig.extra`). Never import the root `env.js` from `src/`.
- To add a variable: add it to the zod schema and to `_clientEnv` (or `_buildTimeEnv`) in `env.js`. Then add it to `.env.example`, to every workflow that writes `.env.*` files, and to EAS env vars.
- Client variables: `APP_ENV`, `NAME`, `SCHEME`, `BUNDLE_ID`, `PACKAGE`, `VERSION`, `YADIO_API_URL`, `MEMPOOL_URL`, `BREEZ_API_KEY`, `NOTIFICATION_API_URL`.
- Package or bundle id per environment:
  - production: `com.grimm.labs.app`
  - staging: `com.grimm.labs.app.staging`
  - development: `com.grimm.labs.app.development`
- HTTP clients live in `src/api/common/client.tsx` (`yadioClient`, `mempoolClient`) and `src/api/notifications/client.ts`. Hooks use react-query-kit, currently always `createMutation` (even for GETs). `@/api/mempool` is not re-exported from `@/api`.

### Notifications

- Permission is requested in two places only:
  - on onboarding "Get started" (`requestNotificationPermissions`, errors are swallowed);
  - from `settings/notifications.tsx`.
- The device is registered with the notification service only when a seed exists **and** permission is already granted. It is re-synced when the app returns to the foreground (60 s debounce).
- A missing Firebase config does not crash the app at runtime: the errors are mapped to `FcmNotConfiguredError` and caught. It does break the **Android build** (see "Gotchas").

### i18n

- `src/lib/i18n` initializes i18next as a side effect of importing `@/lib`. `t()` keys are type-checked against `en.json`.
- Every key must exist in **both** `en.json` and `fr.json`, with identical key sets and keys sorted. Run `pnpm lint:translations` to sort them. Interpolation uses `{{var}}`.
- Don't hardcode user-facing strings. The 404 screen and the wallet error boundaries still do; don't copy that.

### UI conventions

- Use the primitives from `@/components/ui`: `Text` (supports `tx` for translation keys), `Button` (variants `default|secondary|outline|destructive|ghost|link`, sizes `default|lg|sm|icon`, `loading`, `fullWidth`), `Input`/`ControlledInput`, `Select`, `Modal`, `Checkbox/Radio/Switch`, `Image`, `SafeAreaView`, `colors`.
- Style with `className`. For theme-aware class sets use `theme` from `@/lib/theme-classes` (`theme.screen`, `theme.textPrimary`, `theme.textSecondary`…). Dark mode is class-based. For non-className APIs (icons, tab bar), use `useColorScheme()` from nativewind with `colors`.
- Typical screen: `SafeAreaProvider` › `SafeAreaView` (class `flex-1` + `theme.screen`), then `Stack.Screen` (options `headerTitle` rendering `HeaderTitle`, `headerLeft: HeaderLeft`…) and `FocusAwareStatusBar`. `need-help.tsx` is a good reference.
- **testIDs**: kebab-case, prefixed with the screen (`onboarding-get-started`, `need-help-item-call`). `Button` and `Input` derive `${testID}-label` and `${testID}-error`. Maestro flows depend on these ids: don't rename them without updating `.maestro/`. Add testIDs to anything a future E2E flow will need to tap or assert.

## Code style (enforced by ESLint)

- Filenames are **kebab-case** (`unicorn/filename-case`).
- Prettier: single quotes, `printWidth: 220`.
- Imports use `import type` for types (`consistent-type-imports`). They are sorted by `simple-import-sort`: external packages, blank line, `@/…`, blank line, relative. There must be no unused imports; prefix unused vars with `_`.
- `max-params: 3` (use an options object). `max-lines-per-function: 70`: many screens disable it at file level. Prefer extracting components over adding more disables.
- `tailwindcss/classnames-order`, `no-secrets` (file-level disable is accepted for long i18n keys), `plugin:security` (`detect-object-injection` disables are common).
- Use the `@/` alias for anything in `src/`.
- Commits follow Conventional Commits (`feat:`, `fix:`, `refactor:`…), checked by commitlint. Branches are often `<issue-number>-<slug>`.
- The husky `pre-commit` hook **refuses commits on `main`/`master`** (unless `SKIP_BRANCH_PROTECTION` is set), then runs `pnpm type-check` and lint-staged.

## Unit tests (Jest)

- Tests live in `__tests__/` folders next to the code, or as colocated `*.test.tsx` files. `.eslintignore` excludes `__tests__/`, so only colocated tests are linted.
- `jest-setup.ts` mocks AsyncStorage and `useModalBottomInset`. `src/lib/test-utils.tsx` provides `render`/`setup` wrapped in `NavigationContainer` + `BottomSheetModalProvider`.
- Screen tests mock their dependencies inline:
  - `react-i18next` (assertions then use raw keys such as `'onboarding.title'`)
  - `expo-router`
  - `react-native-safe-area-context`
  - `@expo/vector-icons/Ionicons`
  - `@/components/ui/focus-aware-status-bar`
  - the contexts they use (`@/lib/context`, `breez-context`, …)

  Copy the pattern from `src/app/__tests__/onboarding.test.tsx` or `src/app/send/__tests__/*.test.tsx`.

- Give the translation mock a **stable** `t`: declare `const mockT = (key: string) => key;` at module scope and mock `useTranslation: () => ({ t: mockT })`. An inline `t: (k) => k` creates a new function on every render. Screens with `t` in `useCallback`/`useEffect` deps then loop forever and `waitFor` times out.
- `transformIgnorePatterns` does not transform `@breeztech/*`. Anything that imports the Breez SDK must mock `@breeztech/breez-sdk-spark-react-native` or `@/lib/context/breez-context`.
- For BDK, put `jest.mock('bdk-rn', () => require('@/lib/bdk/__tests__/helpers/mock-bdk-rn'))` before the imports.
- `src/components/__tests__/screen-capture-guard.test.tsx` builds a full `AppContext` value. When you add a field to `AppContext`, add it there too or `pnpm type-check` fails.
- `jest.mock` factories may only reference variables prefixed with `mock`.

## E2E tests (Maestro)

Layout:

```text
.maestro/
  config.yaml                 # flows: ['*'] → every flow at the root is a test
  onboarding.yaml             # tags: smoke, onboarding
  need-help.yaml              # tags: smoke, onboarding
  subflows/
    launch-fresh-app.yaml     # launchApp(clearState) + wait up to 60 s for onboarding-screen
```

Rules for new flows:

- Put one test per file at the root of `.maestro/`, with header `appId: ${APP_ID}`, a `name:` and `tags:`. Put reusable steps in `subflows/` and call them with `runFlow: subflows/<file>.yaml`. Files in subfolders are not run as tests.
- Each flow must be independent: start with `runFlow: subflows/launch-fresh-app.yaml` (or another subflow that sets up its state). Don't depend on the order of execution.
- Select elements by `id` (the React Native `testID`), not by text: the UI is translated and the device locale can change. After navigation or network calls, use `extendedWaitUntil` rather than bare `assertVisible`.
- `launchApp` grants all permissions by default, so the Android 13+ notification prompt does not appear after "Get started".
- Flows that create a wallet talk to real services: Breez (needs `BREEZ_API_KEY`), Esplora/mempool, the notification service. Prefer testnet, and never use a funded mainnet seed.

Running locally:

```sh
pnpm android --variant release     # development env, release build (JS embedded), built for the connected device's ABI only
pnpm e2e-test                      # = maestro test .maestro/ -e APP_ID=com.grimm.labs.app.development
maestro test .maestro/need-help.yaml -e APP_ID=com.grimm.labs.app.development   # a single flow
maestro test .maestro/ -e APP_ID=com.grimm.labs.app.development --include-tags smoke
```

Use a **release** build. A debug build contains `expo-dev-client`: after `clearState` it opens the Expo dev launcher instead of the app. The development variant matches the committed `android/` project, so this needs no prebuild. It does need `.env.development` and `credentials/firebase/google-services.json` locally.

Use an **arm64 device or emulator** (Apple Silicon emulators are fine). CI pins Maestro `2.10.0` (`MAESTRO_VERSION` in `e2e-android.yml`); use the same version locally (`curl -Ls "https://get.maestro.mobile.dev" | MAESTRO_VERSION=2.10.0 bash`).

In CI, `e2e-android.yml` is the only E2E pipeline (we don't use Maestro Cloud). It runs on every pull request and every push to `master` (markdown-only changes are skipped), and can be started manually:

- Job 1 builds a **staging release APK for `arm64-v8a` only** with `.github/actions/setup-jdk-generate-apk`.
- Job 2 runs the flows on a GitHub-hosted emulator: API 35 `google_apis` x86_64 with KVM, which translates ARM code.
- Reports go in the `e2e-android-report` artifact: JUnit, Maestro debug output, and logcat on failure.
- A full run takes about 25 minutes (about 16 of them for the Gradle build).

## Builds, environments and CI

- `android/` and `ios/` are **committed** prebuild output. The committed Android project is the development variant. `pnpm prebuild:<env>` rewrites them (package name, icons…). Don't commit an accidental prebuild for another environment, and keep native changes reproducible through `app.config.ts`/config plugins.
- `android/app/build.gradle` always applies the Google Services plugin, so **every Android build needs `google-services.json`**. It lives in `credentials/firebase/google-services.json` (gitignored); `app.config.ts` picks it up and prebuild copies it into `android/app/`.
  - For CI builds, it comes from the base64 secret `GOOGLE_SERVICES_JSON`.
  - For EAS builds, it comes from an EAS file variable, copied by the `eas-build-pre-install` script. EAS does not upload gitignored files, so a file created on the GitHub runner never reaches the EAS build server.
  - `credentials/firebase/google-services.example.json` is enough to build, but push notifications won't work with it.
- EAS profiles (`eas.json`):
  - `development`, `staging` (internal APK) and `production` (store AAB, auto-increment, arm-only ABIs `armeabi-v7a,arm64-v8a`);
  - plus `simulator`.
  - Versions come from EAS (`appVersionSource: remote`).
- Release process:
  1. The `new-app-version` workflow (or `pnpm app-release`, which uses `np`) bumps the version and pushes a tag.
  2. `new-github-release` creates a draft release.
  3. Publishing the release triggers the EAS QA (staging) and development builds.
  4. `eas-build-prod` is manual.
- CI checks on PRs to master: `lint-ts`, `type-check`, `test` (with a coverage comment), `codeql`, `e2e-android`, and `security-audit`/`expo-doctor` when `package.json`/lockfile change.
- Workflows create `.env.<env>` from the secret `BREEZ_API_KEY` and the variables `NOTIFICATION_API_URL_{DEV,STAGING,PROD}`.

## Gotchas

- **bdk-rn is arm64-only on Android.** Its `libbdkffi.a` exists only for `arm64-v8a`, and its Gradle config restricts the ABI to that. An APK that contains another ABI folder (x86_64, armeabi-v7a) is missing `libbdk-rn.so` for that ABI, and the app crashes at startup on such devices. This is why the E2E APK is built with `-PreactNativeArchitectures=arm64-v8a`. The production AAB also ships `armeabi-v7a`, so 32-bit ARM devices are affected.
- The root `env.js` throws on missing variables. Any command that evaluates the Expo config (prebuild, Gradle JS bundling, `expo config`) needs `.env.<APP_ENV>`.
- The same Breez `storageDir` is shared between networks, and the testnet/regtest mapping is inconsistent (see "Wallets and networks").
- Background pollers (Breez 10 s, BDK 60 s + 30 s retry, prices 20 s) run from providers. Avoid adding more intervals; reuse the existing refresh functions.
- `.husky/post-merge` looks for `pnpm-lock.yml` (typo), so it never auto-installs after a merge.
